# Nero 버전 관리

## 기준

- 제품 번호는 `0.0.1`로 재기준을 잡는다. 외부 사용자 호환성 기준은 실제 첫 공유 시점의 제품 버전, 빌드와 최종 소스 커밋을 배포 영수증에 기록해 정한다. GitHub에 개발용 릴리스가 존재했다는 이유만으로 외부 사용자 공유가 완료됐다고 간주하지 않는다.
- 첫 외부 공유 전 이번 한 번에 한해 GitHub 릴리스, 해당 릴리스 태그와 공개 릴리스 문서를 초기화한다. 제품은 `0.0.1`부터 다시 시작하되 독립 빌드 번호는 계속 증가시킨다. Git 커밋과 필요한 비공개 소스/서명/공증 증거는 보존한다.
- 초기화 범위는 릴리스 기록뿐이다. 기존 개인 회의, 원음, 메모, 수정본, 요약, 모델, 연동과 인증 정보는 보존한다. 앱 식별자, 저장 경로, 모델 pin과 서명 키도 변경하지 않는다.
- 이 예외 이후 외부 사용자에게 공유한 설치 파일과 태그는 덮어쓰지 않는다. 서명/공증/빌드 성공과 실제 설치/업데이트 수락은 구분해 확인한다.
- 첫 공유 전에도 저장 형식/경로 변경이 기존 데이터에 영향을 주면 명시적으로 이관하거나 별도 보관한다. 읽기 실패를 삭제/초기화로 해결하지 않는다. 과거 개발 형식의 리더를 계속 유지할 의무와 실제 데이터 보존은 구분한다.

### 기존 개발 설치본 전환

기존 빌드49에서 `0.0.1`/빌드50으로 바꾸는 작업은 제품 버전 재기준에 따른 수동 전환이다. 일반 버전 설정 도구, 자동 업데이트의 제품 버전 하향 거부와 Windows NSIS의 하향 설치 보호는 유지한다. 빌드 번호가50으로 커졌다고 기존 앱이 낮아진 제품 버전을 자동 업데이트로 받아들인다고 안내하지 않는다.

전환은 명시적으로 허용한 앱 교체 절차로 수행하고 기존 데이터, 모델과 연동을 대조한다. Windows에서 제거 후 설치가 필요하면 앱 데이터 삭제를 선택하지 않는다. 기존 앱을 강제 종료하거나 데이터 폴더를 초기화하지 않는다.

## 번호

| 구분 | 규칙 |
|---|---|
| 제품 버전 `MAJOR.MINOR.PATCH` | 첫 공유 전에는 `0.0.1`로 개발 가능. 첫 공유 후 `PATCH`는 호환 버그 수정, `MINOR`는 호환 기능 추가, `MAJOR`는 명시적인 비호환 계약 변경에 사용. `0.x`라는 이유로 공유된 데이터를 임의로 깨지 않음 |
| 배포 빌드 | `1`부터 시작하는 양의 정수. 제품 버전과 독립적으로 증가시키며 재사용하지 않음. 첫 공유 전에는 같은 제품 버전의 개발 변경을 새 빌드로 구분. 기존 산출물을 덮어쓰지 않으며 첫 공유 후에는 사용자에게 제공하는 변경본의 제품 버전도 증가 |
| 저장 스키마 | 제품 버전과 독립. 저장 필드/값/의미가 바뀌는지로 결정하며 제품 번호만 바뀌면 올리지 않음 |
| 문서 수정 회차 | `TranscriptVersion.revision`은 해당 음성 기록의 편집 회차. 제품/스키마 버전으로 사용하지 않음 |
| 모델/프롬프트 | 모델 revision/SHA256, 실행기, `promptVersion`, 템플릿을 결과에 보존. 앱 버전으로 대체하지 않음 |
| CLI/연결 패키지 | `apps/desktop/agent/release.json`의 `integrationVersion`으로 제품/빌드와 별도 관리. 이번 세대는 `0.3.0-nero.35`로 증가하며 제품의 `0.0.1` 재기준에 맞춰 낮추지 않음. CLI, API, 스킬과 패키지 템플릿 변경 시 증가. UI만 변경된 배포에서 동일한 서명 컴포넌트를 검증 후 재사용하면 실제 연결 세대도 유지 |

제품 버전의 정본은 `apps/desktop/package.json`의 `version`이다. `node apps/desktop/scripts/version.mjs set <version> --build <number>`로 Tauri 설정, core/desktop/CLI Rust 패키지와 npm/Cargo 잠금 파일을 함께 갱신하고, `node apps/desktop/scripts/version.mjs check`로 일치 여부를 검사한다.

- macOS는 제품 버전을 표시 버전으로, `bundle.macOS.bundleVersion`을 `CFBundleVersion`으로 사용한다. 현재 제품 버전은 위 정본을 따르며 최종 배포 빌드는 설치 파일의 영수증에서 확인한다.
- Windows NSIS 설치 버전은 현재 제품 버전과 같다. 독립 빌드 번호는 배포 파일명/영수증에 기록한다. 별도 네 번째 설치 버전 필드가 구현됐다고 가정하지 않는다.
- 현재 패키지, 이벤트, 앱 식별자와 새 저장 위치는 Nero 이름을 사용한다. 이전 식별자는 명시적인 기존 데이터 이전 코드와 과거 원본 증거에만 남긴다.
- 사용자 릴리스 태그는 `v<제품 버전>`으로 최종 릴리스 구성 커밋에 붙인다. 위 1회 초기화에서 제거한 개발용 `v0.0.1`은 새 기준의 최종 커밋에 새로 만든다. 이후 공유한 태그는 이동하거나 재사용하지 않으며, 새 개발 빌드마다 제품 버전 태그를 만들 필요는 없다. 이미 공증된 앱을 컨테이너만 다시 포장하면 앱 소스와 포장 도구 커밋을 각각 기록한다. 문서만 후속 커밋으로 보강해도 배포본의 소스 해시는 바꾸지 않는다.

## 현재 저장 구조

현재 지원하는 저장 구조다. 변경 시 지원 대상 버전의 데이터를 보존하는 읽기/이관 경로와 실패 복구를 확인한다.

| 대상 | 현재 계약 |
|---|---|
| 앱 식별자 | `io.github.choseongmin1128.nero.desktop` |
| 저장 루트 | Tauri `app_data_dir()`. macOS는 `~/Library/Application Support/<identifier>`, Windows는 해당 사용자의 앱 데이터 디렉터리. 제품 이름/버전으로 새 경로를 조립하지 않음 |
| 회의 `meeting.json` / 녹음 `manifest.json` | `store.rs`의 `SCHEMA_VERSION = 1`; 다른 schemaVersion은 현재 읽기 거부 |
| 음성 기록/회의록 | 별도 schemaVersion 필드 없음. `Transcript`, `TranscriptSegment`, `Summary`의 JSON 구조가 현재 계약이며, 수정 회차/원문 해시는 별도로 저장 |
| 추가된 선택 필드 | `meetingDate`, `recordedAt`, `warning`, 녹음 `quality`, 저장 기본 제목 출처 `generatedTitle`, 일정 시작일 `startDate`는 없는 기존 데이터를 기본값으로 읽음 |
| 원본 | 녹음 PCM, 가져온 원본, 모델 원출력을 보존. 수정본/회의록은 별도 결과로 저장 |

데이터를 쓰는 경로는 `CoreHandle`의 직렬 처리와 `Store` 잠금을 통한다. CLI 등 새 진입점을 추가해도 별도 저장소 writer를 만들지 않는다. JSON 교체는 완전한 임시 파일을 쓴 뒤 수행하는 기존 경로를 사용한다.

읽기 전용 CLI/MCP는 `LibraryReader`를 공유하며 writer 잠금, 복구와 마이그레이션을 실행하지 않는다. 연동 응답의 `apiVersion`, 파일 묶음 해시 `sourceVersion`, 음성 기록의 편집 회차는 각각 구분한다. 명시적 수정/삭제 명령은 조회 경로와 구분하고, 회의 변경은 실행 중인 앱의 인증된 writer와 수정 버전 확인을 통한다. 템플릿 변경은 공통 카탈로그 잠금과 revision 검사를 사용한다.

## 데이터 변경

첫 공유 전:

- 구조/형식을 개선하기 위해 과거 개발 코드의 읽기 경로를 유지할 필요는 없다. 실제 데이터에 대한 이관 또는 별도 보관 방법을 정한 뒤 변경한다.
- 원음, 메모, 수정본, 회의록의 출처 연결을 보존한다. 개인 원문은 공개 테스트에 넣지 않는다. 형식 변환이 필요하면 입력/출력 형식과 백업을 명시하고 실패/중단/재실행을 검증한다.
- 지원하지 않는 형식은 오류로 알리고 보존한다. 자동 초기화나 원본의 제자리 파괴를 변경 편의 수단으로 사용하지 않는다.
- 사용처가 없는 호환 계층이나 마이그레이션 프레임워크를 미리 만들지 않는다.

첫 공유 후:

1. 저장 필드의 추가/삭제/이름/타입/의미, enum 값, 경로와 ID, 원문 해시에 영향을 주는 직렬화 변경을 먼저 확인한다. 메모리 안에서만 쓰는 DTO 변경과 구분한다.
2. 누락 가능한 필드 추가는 지원하는 기존 파일에서 기본값으로 읽을 수 있게 한다. 필수 필드나 enum 값 변경은 단순 선택 필드 추가로 취급하지 않는다.
3. 새 코드가 지원 대상 이전 릴리스 데이터를 읽고 편집/재개방해도 원음, 메모, 수정본, 회의록의 출처 연결을 보존해야 한다. 필요한 변환은 명시적인 이관으로 제공하며, 원본 백업과 실패 복구를 검증한다.
4. 지원하지 않는 형식/버전은 오류로 알리고 데이터를 보존한다. 읽기 실패를 빈 라이브러리로 처리하거나 자동 삭제/초기화하지 않는다.

두 단계 모두 모델을 바꾸거나 재처리해도 기존 결과를 삭제하지 않는다. 전사 수정 버전/해시와 다르면 회의록이 오래된 결과임을 유지한다.

현재 저장 구조는 `deny_unknown_fields`를 사용하므로, 새 앱이 추가한 필드를 오래된 앱이 읽는 역방향 호환은 보장되지 않는다. 첫 공유 후 하위호환성의 기본 보장은 **새 버전이 지원 대상 이전 버전의 데이터를 보존하는 것**이다. 구버전으로 되돌릴 때는 그 구버전에 맞는 백업 사본을 별도 경로에서 사용해야 하며, 최신 데이터를 구버전으로 열어도 된다고 안내하지 않는다.

## 릴리스 확인

- 제품/플랫폼 버전, 앱 식별자, 저장 스키마, 모델/프롬프트 변경 여부를 확인한다.
- 첫 공유 전 저장 형식 변경은 영향받는 기존 데이터의 이관/보관을 검증한다. 첫 공유 후에는 지원 대상 이전 배포 형식의 익명 fixture로 읽기, 수정, 재개방, 출처 연결을 검증한다. 현재 구조의 왕복 테스트만으로 이전 버전 호환을 통과 처리하지 않는다.
- 저장 형식이 그대로면 불필요한 마이그레이션을 실행하지 않는다. 실제 설치본 교체 시 원본 데이터/모델 보존 여부를 별도 확인한다.
- macOS 서명/공증/DMG와 Windows 설치/업데이트는 별도 검증이다. 한 운영체제의 통과를 다른 운영체제 통과로 기록하지 않는다.
- 소스 commit 전체 해시, dirty 여부, 빌드 번호, 산출물 SHA256, 대상 OS/아키텍처와 확인 범위를 이력에 기록한다. 미커밋 빌드는 기준 HEAD와 변경 소스 해시/패치를 보존하고, HEAD만으로 재현 가능하다고 쓰지 않는다.
- 배포 앱의 `Contents/Resources/build-info.json`과 ZIP/DMG 각각의 `.zip.receipt.json`/`.dmg.receipt.json`에 동일한 소스 정보를 남긴다. 실제 배포 서명은 미커밋 소스나 빌드 후 소스 변경을 거부한다.
- 소스 변경 이력과 실제 배포/공증/설치 상태를 구분한다. 존재하지 않는 커밋 해시나 아직 받지 않은 공증 승인을 기입하지 않는다.

변경 및 배포 기록은 [릴리스 이력](release-history.md)에 남긴다.

설치 시 저장 metadata를 확장하면 같은 소스의 CLI/MCP reader도 함께 준비하고 연동 패키지 세대를 갱신한다. 구형 reader의 엄격한 필드 검증을 무시하거나 사용자 원본에서 필드를 지워 맞추지 않는다.
